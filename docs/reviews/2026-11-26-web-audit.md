# Web app audit against the autoplan review

- Date: 2026-11-26 · Scope: `apps/web` (Next.js), checked against the web-facing amendments in [`2026-11-19-autoplan-review.md`](2026-11-19-autoplan-review.md): A-DES-1 to A-DES-7, A-ENG-3 and A-CEO-6.
- Mode: report only. No app code was changed.
- gstack: only the `/gstack` router is installed in this session (`/qa-only` is not), so the QA checklist was run by hand.

## How it was tested

- **Production build** (`pnpm build && pnpm start`). Lint, typecheck and the 122 vitest tests pass.
- **Cloud API:** Docker Hub returned `429 Too Many Requests`, so Postgres and the API could not start. A Playwright stand-in returned realistic responses built from the types in `src/lib/api.ts` (an owner on the Workshop plan, one open job with codes, alerts and an AI diagnosis, and one closed job).
- **Vehicle:** the built-in browser demo car (`rootcause.edgeMode = browser-sim`).
- **Pages crawled:** 22 routes in night mode, and 5 of them again in daylight mode. Each page got:
  - axe-core checks (WCAG 2 A/AA and best practice),
  - a scan for buttons, links and inputs smaller than 40 px,
  - a capture of console errors and full-page screenshots.
- **Failure runs:** the same crawl with every API call returning HTTP 500, and again with the API unreachable.
- **Flow walk:** connect the demo adapter → open a job → scan all modules → live data → service functions → CAN Studio.
- **By code only:** the safety confirm, CAN Studio's 29-bit IDs and the version banner can't be exercised with the read-only demo car, so these were checked by reading the code.

## Findings, most serious first

| # | Severity | Amendment | Finding | Where |
| --- | --- | --- | --- | --- |
| 1 | Medium | A-DES-3 | **A hold can complete after a safety check fails mid-hold.** `startHold` runs a requestAnimationFrame loop that never re-checks `canHold`. If speed or RPM goes bad during the 1.5 s, the button becomes `disabled`, which stops its pointer and key events, so `stopHold` may never run and `onConfirm` still fires. Moving focus away mid-hold has the same effect. The daemon refuses the request anyway (Rule 5), so the vehicle is protected, but the UI shows a confirmation the checks no longer support. Fix: stop the hold when `canHold` turns false, and on `blur`. | `components/safety/SafetyConfirmModal.tsx:106-122`, `:252` |
| 2 | Medium | A-DES-3, Rule 5 | **The confirm button allows holding when a reading is unknown.** Only `fail` blocks the hold; `unknown` ("no reading") does not, and readings carry no age, so a value older than the 2 s freshness rule still shows as OK. The daemon then refuses with `PRECONDITION_UNKNOWN`. The UI should fail closed like the daemon does: treat unknown or stale as blocking, and say why. | `SafetyConfirmModal.tsx:37-61`, `:84` |
| 3 | Medium | A-DES-2 | **Home, Workshop and the admin pages go blank when the cloud is unreachable.** Each one does `if (!me) return null`, so the user sees only the "Working offline" banner, even though that banner says "Vehicle reading keeps working". With no page content, there's no way to start a job or reach the vehicle tools. Show the page with an offline state. | `app/(app)/home/page.tsx:49`, `app/(app)/workshop/page.tsx:18`, `app/(app)/admin/layout.tsx:9` |
| 4 | Medium | A-DES-2 | **Live data has no "stream stalled" state.** The review's state table requires one when no sample arrives for more than 2 s. Today the charts just freeze with no message. | `app/(app)/jobs/[id]/live/page.tsx` |
| 5 | Medium | A-DES-6 | **Many controls are below the 44 px touch target.** | see below |
| 6 | Low | A-DES-6 | **Daylight contrast fails on blue badges.** `--blue-ink #0b5ad9` on `--blue-soft` measures 4.27:1 at 12 px (WCAG AA needs 4.5:1). This is the "Open" status badge on the job page. Darken the ink to about `#0a4fc0`. | `app/globals.css:40`, `:49` |
| 7 | Low | A-DES-2 | **Misleading audit message on a different adapter.** When the job was started on another adapter, the audit says "Connect the vehicle to run the audit" although a vehicle is connected. The "different adapter" banner above it is correct; the audit line should say the same. | `components/job/AlertsCard.tsx:83`, `:101` |
| 8 | Low | A-DES-6 | **The job page heading includes its status badge.** The `<h1>` reads as "2008 BMW 320i (E90) i Open", so screen readers announce the icon letter. Move the badge out of the heading or mark the icon `aria-hidden`. | job layout header |
| 9 | Low | A-DES-2 | **Error messages show the server's `detail` text verbatim.** For example, "Couldn't load this job: boom" with a test response. This is fine while the API returns plain-English details; make sure it never returns stack or debug text. | `lib/api.ts:81-89` |

**Finding 5 detail.** Touch targets under 44 px:
- **The `size="sm"` button (36 px)** in `components/ui.tsx:37`, `:65`, `:306`. It's used for primary bay actions: Scan all modules, Clear codes, Retry, Use the real daemon, Connect, the Open/Closed/All filter, and Monthly/Annual.
- **Native checkboxes at 13 × 16 px:** Start a job, Key programming, Close out.
- **The "Evidence" disclosure** on alerts: 16 px tall.
- **Small inline links** such as "Submit it below" (15 px).
- **The sidebar logo link:** 32 px tall.

The simplest fix is to make `sm` 44 px tall and keep it compact with smaller horizontal padding, then wrap checkboxes in a 44 px label.

## Not covered

- Tablet and phone widths. Phone layouts are out of scope in the review; a tablet pass is worth doing before workshop beta.

3. Findings 3 and 4: offline page shells and the live-data stall banner.
4. Findings 6 to 9.
